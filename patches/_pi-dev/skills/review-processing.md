# Обработка замечаний ревью
Аргументы команды приходят в конце скилла как `User: …`: номер или ссылка PR/MR заменяет поиск по ветке, остальное – дополнительные указания.

## Ограничения
- С GitHub и GitLab работать только через их MCP.
- Не коммитить и не пушить: ключ для подписи и авторизации только у меня.
- Отвечать ревьюеру и закрывать тред только по замечаниям, исправленным в этом запуске. Остальное не трогать: не отвечать, не закрывать, реакции не ставить – на это отвечу сам.
- Ответ ревьюеру – ровно одно слово `Исправил`, без пояснений. Единственное исключение – ответ на одиночный комментарий в GitHub, описанный в разделе ответов.
- Исправлять только то, о чём замечание, код вне его scope не трогать. Соблюдать инструкции репозитория: `AGENTS.md`, `CLAUDE.md` и подобные.

## Платформа, PR/MR и рабочая копия
- Ветка – `git branch --show-current`, remote – тот, на который настроен upstream ветки, а без upstream – `origin`.
- Из URL remote взять хост и путь без `.git`, разбирая формы `https://`, `git@host:` и `ssh://` с портом. Хост `github.com` – GitHub, путь – `<владелец>/<репо>`. Любой другой хост – GitLab, путь – `<группа>/…/<проект>`.
- Найти открытый PR/MR текущей ветки:
  - GitHub – `list_pull_requests` с `state: open` и `head: <владелец>:<ветка>`, а если пусто, например PR из форка, – `search_pull_requests` с запросом `is:pr is:open head:<ветка>` и выбрать PR, у которого head-репозиторий совпадает с remote;
  - GitLab – `list_merge_requests` с `project_id` – путём проекта, `source_branch` – веткой и `state: opened`.
- Если номер или ссылка PR/MR переданы аргументом – взять их, но сверить исходную ветку PR/MR с текущей. При расхождении остановиться и спросить меня.
- Если PR/MR не найден или подходящих несколько – остановиться и спросить меня.
- Свой логин получить через `get_me` в GitHub или `whoami` в GitLab.
- Сверить рабочую копию с PR/MR, не запуская `git fetch`. Последний коммит PR/MR – `head.sha` из `pull_request_read` с `method: get` в GitHub или `sha` из `get_merge_request` в GitLab:
  - если этого коммита нет локально или `git merge-base --is-ancestor <sha> HEAD` завершается неуспешно – локальная ветка отстала или разошлась с PR/MR: остановиться и спросить меня;
  - если `HEAD` впереди или в рабочем дереве есть незакоммиченные изменения – до начала обработки сообщить в чате коммиты из `git log --oneline <sha>..HEAD` и файлы из `git status --short`, затем продолжить.

## Сбор комментариев
Комментарии бывают двух видов: треды, которые можно закрыть, и одиночные комментарии без треда. Брать оба вида, включая outdated.

### GitHub
- Треды – `pull_request_read` с `method: get_review_comments` и `perPage: 100`, все страницы через `after` со значением `endCursor`. Брать все, которые не resolved, в том числе outdated.
- Одиночные комментарии, аналог `individual_note` в GitLab, – общие комментарии PR из `method: get_comments` и тексты ревью с непустым `body` из `method: get_reviews`, все страницы через `page` и `perPage: 100`. Закрыть их нельзя, поэтому открытым считать такой комментарий, автор которого не я и на который после него нет моего ответа со ссылкой на него.

### GitLab
- Discussions – `mr_discussions` с `per_page: 100`, все страницы, пока страница не вернётся неполной. По умолчанию отдаётся только 20 записей, поэтому без пагинации часть комментариев теряется.
- Заметки с `system: true` пропускать.
- Треды – discussions с `individual_note: false`, у которых есть заметка с `resolvable: true` и `resolved: false`, в том числе outdated `DiffNote`, чья позиция относится к старой версии diff.
- Одиночные комментарии – discussions с `individual_note: true`, автор которых не я. Они не resolvable, пока на них никто не ответил.

### Общие правила
- Resolved треды не трогать.
- Читать каждый тред целиком: последующие комментарии могут уточнять или отменять замечание, а мои ответы в треде учитывать как уже принятое решение.
- Для outdated тредов сверять замечание с текущим кодом по координатам и тексту, потому что код мог сместиться или уже измениться: в GitHub – по `path` и исходным строкам, в GitLab – по `position`.
- В одиночных комментариях и текстах ревью находить ссылки на код – файлы, строки, коммиты, фрагменты diff – и разбирать каждое замечание из них по текущему коду так же, как тред.
- Если в одном комментарии несколько замечаний, отвечать и закрывать его только после исправления всех. При частичном исправлении не отвечать и не закрывать, а в отчёте перечислить, что исправлено и что нет.

## Оценка замечания
Треды и одиночные комментарии обрабатывать по одному, до конца:
1. Проверить замечание по текущему коду: верно ли оно для этой кодовой базы, не ломает ли существующее поведение, не противоречит ли инструкциям репозитория, другим замечаниям и моим решениям.
2. Если замечание требует «сделать как положено» – добавить обработку ошибок, метрики, параметры, абстракции – сначала найти через grep реальное использование затронутого кода. Если код никем не вызывается или сценарий невозможен – это несогласие с аргументом, а не правка.
3. Если замечание неясно – не исправлять ни его, ни связанные с ним замечания, пока я не отвечу: тот же код, та же тема или правки зависят друг от друга. Вопрос по каждому такому замечанию вынести в отчёт.
4. Если не согласна, замечание уже исправлено до запуска или нужно моё решение – в PR/MR ничего не делать и перейти к следующему.
5. Если согласна – исправить и проверить правку линтерами и быстрыми проверками для затронутых файлов, затем сразу ответить и закрыть.

## Ответ и закрытие
Отвечать и закрывать сразу после исправления, не откладывая на конец. Если одна правка закрывает несколько тредов или комментариев, каждому ответить и каждый закрыть отдельно.

### GitHub
- Тред – ответить через `add_reply_to_pull_request_comment`: `commentId` – числовой id первого комментария треда из якоря `#discussion_r…`, не node ID треда, `pullNumber` – номер PR, `body` – `Исправил`. Затем закрыть через `pull_request_review_write` с `method: resolve_thread` и `threadId` – node ID треда вида `PRRT_…`.
- Одиночный комментарий или текст ревью – ответить через `add_issue_comment` с `issue_number` – номером PR. В `body` первая строка – ссылка `html_url` исходного комментария или ревью, вторая – `Исправил`. Без ссылки ответ не связан с комментарием, и при следующем запуске не понять, на что уже есть ответ. Закрыть такой комментарий нельзя.

### GitLab
- Ответить через `create_merge_request_discussion_note` с `discussion_id` и `body` – `Исправил`. Ответ на `individual_note` превращает его в тред, который после этого можно закрыть. Новую заметку через `create_merge_request_note` не создавать: она не привязана к треду.
- Закрыть через `resolve_merge_request_thread` с тем же `discussion_id` и `resolved: true`.
- Проверить ответ на закрытие: все заметки треда с `resolvable: true` должны иметь `resolved: true`. Если закрытие вернуло ошибку или тред остался открытым, например бывший `individual_note` ещё не стал resolvable, – заново получить discussions, повторить `resolve_merge_request_thread`, а если не помогло – закрыть каждую заметку треда через `update_merge_request_discussion_note` с её `note_id` и `resolved: true`.

## Итоговая проверка
- Заново получить все треды и комментарии PR/MR со всеми страницами.
- Каждый исправленный тред должен содержать мой ответ `Исправил` и быть закрыт: в GitHub – resolved, в GitLab – все его заметки с `resolvable: true` имеют `resolved: true`, а бывшие `individual_note` искать по их `discussion_id`.
- На каждый исправленный одиночный комментарий в GitHub должен быть мой ответ со ссылкой на него.
- Недоделанное доделать и проверить снова. Если после трёх попыток тред всё ещё открыт или ответа нет – перечислить мне его id, ссылку и полученную ошибку.
- Треды и комментарии, по которым исправлений не было, должны остаться без моих новых ответов и без изменения статуса.

## Отчёт в чате
По каждому открытому треду и одиночному комментарию отдельным пунктом списка, без таблиц:
- ссылка на комментарий, автор и `путь:строка`, если замечание касается кода;
- суть замечания одной строкой;
- решение: исправлено, исправлено частично, не согласна, уже было исправлено, нужно моё решение или нужен ответ на вопрос;
- аргументация решения, для исправленных – что и где изменено, для неясных – вопрос ко мне.
В конце указать результат итоговой проверки, расхождения рабочей копии с PR/MR, если были, и что изменения не закоммичены и не запушены.
