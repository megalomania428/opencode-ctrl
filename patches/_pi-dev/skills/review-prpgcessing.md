# Обработка замечаний ревью
Аргументы команды приходят в конце скилла как `User: …`: номер или ссылка PR/MR заменяет поиск по ветке, остальное – дополнительные указания.

## Ограничения
- С GitHub и GitLab работать только через их MCP.
- Не коммитить и не пушить: ключ для подписи и авторизации только у меня.
- Отвечать ревьюеру и закрывать тред только по замечаниям, исправленным в этом запуске. Остальное не трогать: не отвечать, не закрывать, реакции не ставить – на это отвечу сам.
- Ответ ревьюеру – ровно одно слово `Исправил`, без пояснений. Единственное исключение – ответ на одиночный комментарий в GitHub, описанный в разделе ответов.
- В GitHub отвечать и закрывать сразу после каждого исправления. В GitLab ответы с закрытием собирать в черновики и публиковать один раз в конце.
- Исправлять только то, о чём замечание, код вне его scope не трогать. Соблюдать инструкции репозитория: `AGENTS.md`, `CLAUDE.md` и подобные.

## Платформа, PR/MR и рабочая копия
- Ветка – `git branch --show-current`, remote – тот, на который настроен upstream ветки, а без upstream – `origin`.
- Из URL remote взять хост и путь без `.git`, разбирая формы `https://`, `git@host:` и `ssh://` с портом. Хост `github.com` – GitHub, путь – `<владелец>/<репо>`. Любой другой хост – GitLab, путь – `<группа>/…/<проект>`.
- Найти открытый PR/MR текущей ветки:
  - GitHub – `list_pull_requests` с `state: open` и `head: <владелец>:<ветка>`, а если пусто, например PR из форка, – `search_pull_requests` с запросом `is:pr is:open head:<ветка>` и выбрать PR, у которого head-репозиторий совпадает с remote;
  - GitLab – `list_merge_requests` с `project_id` – путём проекта, `source_branch` – веткой и `state: opened`.
- Если номер или ссылка PR/MR переданы аргументом – взять их, но сверить исходную ветку PR/MR с текущей. При расхождении остановиться и спросить меня.
- Если PR/MR не найден или подходящих несколько – остановиться и спросить меня.
- Свой логин в GitHub – `user.login` первого элемента из `search_pull_requests` с `query: "author:@me"` и `perPage: 1`, а если пусто – из `search_issues` с `query: "is:issue author:@me"` и `perPage: 1`. Брать именно автора `user`, а не `assignee`, `assignees` или другие поля с логинами. Если пусто и там – остановиться и спросить меня. `get_me` не вызывать: он открывает MCP UI. Логин из автора PR не выводить. В GitLab – через `whoami`.
- В GitLab получить мои черновики через `list_draft_notes` и запомнить их `id`: их не изменять и не публиковать.
- Сверить рабочую копию с PR/MR, не запуская `git fetch`. Последний коммит PR/MR – `head.sha` из `pull_request_read` с `method: get` в GitHub или `sha` из `get_merge_request` в GitLab:
  - если этого коммита нет локально или `git merge-base --is-ancestor <sha> HEAD` завершается неуспешно – локальная ветка отстала или разошлась с PR/MR: остановиться и спросить меня;
  - если `HEAD` впереди или в рабочем дереве есть незакоммиченные изменения – до начала обработки сообщить в чате коммиты из `git log --oneline <sha>..HEAD` и файлы из `git status --short`, затем продолжить.

## Сбор комментариев
Комментарии бывают двух видов: треды, которые можно закрыть, и одиночные комментарии без треда. Брать оба вида, включая outdated.

### GitHub
- Треды – `pull_request_read` с `method: get_review_comments` и `perPage: 100`, все страницы через `after` со значением `endCursor`. Брать все, которые не resolved, в том числе outdated.
- Одиночные комментарии, аналог `individual_note` в GitLab, – общие комментарии PR из `method: get_comments` и тексты ревью с непустым `body` из `method: get_reviews`, все страницы через `page` и `perPage: 100`. Закрыть их нельзя, поэтому открытым считать такой комментарий, автор которого не я и ссылки на который нет в моих более поздних комментариях и текстах ревью.

### GitLab
- Discussions – `mr_discussions` с `per_page: 100`, все страницы, пока страница не вернётся неполной. По умолчанию отдаётся только 20 записей, поэтому без пагинации часть комментариев теряется.
- Заметки с `system: true` пропускать.
- Треды – discussions с `individual_note: false`, у которых есть заметка с `resolvable: true` и `resolved: false`, в том числе outdated `DiffNote`, чья позиция относится к старой версии diff.
- Одиночные комментарии – discussions с `individual_note: true`, автор которых не я. Они не resolvable, пока на них никто не ответил.

### Общие правила
- Resolved треды не трогать.
- Читать каждый тред целиком: последующие комментарии могут уточнять или отменять замечание, а мои ответы в треде учитывать как уже принятое решение.
- Для outdated тредов сверять замечание с текущим кодом по координатам и тексту, потому что код мог сместиться или уже измениться: в GitHub – по `path` и исходным строкам, в GitLab – по `position`.
- В одиночных комментариях и текстах ревью находить ссылки на код – файлы, строки, коммиты, фрагменты diff – и разбирать каждое замечание из них по текущему коду так же, как тред.
- Если в одном комментарии несколько замечаний, отвечать и закрывать его только после исправления всех. При частичном исправлении не отвечать и не закрывать, а в отчёте перечислить, что исправлено и что нет.

## Агенты
Обработчик – текущая сессия. Агенты дают ему независимое второе мнение по каждому открытому треду и одиночному комментарию.

### Запуск
- Перед первым запуском в корне репозитория сделать снимок рабочего дерева функцией `snapshot` и передавать его хеш всем агентам. Снимок не создаёт коммитов и не меняет индекс, неотслеживаемые файлы в него попадают, игнорируемые – нет:

```bash
snapshot() {
  local dir
  dir="$(mktemp -d)"
  GIT_INDEX_FILE="${dir}/index" git read-tree HEAD
  GIT_INDEX_FILE="${dir}/index" git add -A
  GIT_INDEX_FILE="${dir}/index" git write-tree
  rm -rf "${dir}"
}
```

- На каждый тред и одиночный комментарий запустить через `spawn_subsession` двух агентов с разными моделями в параметре `model`. Пары моделей чередовать по порядку обработки: `ppg/GLM` и `ppg/qwen`, затем `ppg/qwen` и `ppg/deepseek`, затем `ppg/deepseek` и `ppg/GLM`, и снова по кругу.
- Агентов можно запускать сразу на все треды и комментарии, но одновременно работающих должно быть не больше 7. Запускать в порядке обработки, а освободившиеся места заполнять следующими агентами: проверять `list_subsessions` перед каждым замечанием и после каждого пробуждения от `yield_to_subsessions`.

### Задание агенту
Задание составляет обработчик, и оно должно быть самодостаточным:
- путь к репозиторию и хеш снимка. Код читать только из снимка через `git show "<снимок>:<путь>"` и `git grep <шаблон> "<снимок>"`, потому что рабочую копию в это время меняет обработчик;
- платформа, номер, ссылка, заголовок и описание PR/MR;
- тред или одиночный комментарий целиком: все комментарии с авторами, ссылка, `путь:строка`, признак outdated, diff hunk в GitHub или `position` в GitLab;
- мои ответы в треде как уже принятое решение;
- всё остальное из GitHub или GitLab, что может понадобиться для оценки: связанные треды и комментарии, тексты ревью, issue, коммиты PR/MR. Обработчик заранее получает это сам через MCP и вставляет в задание;
- критерии оценки – шаги 1–3 раздела «Оценка замечания» и инструкции репозитория: `AGENTS.md`, `CLAUDE.md` и подобные;
- прямой запрет обращаться к MCP GitHub и GitLab, а также к GitHub и GitLab любым другим способом: `gh`, `glab`, HTTP API, браузер. Если информации не хватает – не искать её там, а перечислить недостающее в ответе;
- запрет инструментов `spawn_*`, изменения любых файлов, коммитов и тяжёлых тестов;
- формат ответа:
  - первая строка – вердикт `FIX`, `DISAGREE`, `ALREADY_FIXED`, `UNCLEAR` или `NEEDS_DECISION`;
  - дальше кратко аргументы со ссылками `путь:строка` по снимку и конкретными сценариями поломки;
  - при `FIX` – предлагаемое исправление в виде unified diff относительно снимка;
  - при нехватке информации – строка `MISSING:` с перечнем недостающего.

### Учёт ответов
- Ответы агентов по замечанию открывать только после собственного решения по нему. Если агенты этого замечания ещё работают – дождаться их через `yield_to_subsessions`.
- Модели агентов намного слабее модели обработчика, поэтому их ответы ниже по приоритету, чем собственное решение:
  - вердикт агентов не заменяет собственный, даже если оба агента согласны между собой;
  - собственное решение менять только если агент указал упущенный факт или сценарий поломки и он подтвердился собственной проверкой по текущему коду;
  - при расхождении без такого подтверждения оставлять собственное решение;
  - предложенный агентом diff – только подсказка, без проверки его не применять;
  - ссылки агентов относятся к снимку: учитывать, что после него код мог измениться собственными исправлениями.
- Сбой или пустой ответ агента не блокирует обработку: не перезапускать его, а упомянуть в отчёте.

## Оценка замечания
Треды и одиночные комментарии обрабатывать по одному, до конца. Решение сначала принимать самостоятельно, затем сверять с ответами агентов по разделу «Агенты» и действовать по итоговому решению:
1. Проверить замечание по текущему коду: верно ли оно для этой кодовой базы, не ломает ли существующее поведение, не противоречит ли инструкциям репозитория, другим замечаниям и моим решениям.
2. Если замечание требует «сделать как положено» – добавить обработку ошибок, метрики, параметры, абстракции – сначала найти через grep реальное использование затронутого кода. Если код никем не вызывается или сценарий невозможен – это несогласие с аргументом, а не правка.
3. Если замечание неясно – не исправлять ни его, ни связанные с ним замечания, пока я не отвечу: тот же код, та же тема или правки зависят друг от друга. Вопрос по каждому такому замечанию вынести в отчёт.
4. Если не согласна, замечание уже исправлено до запуска или нужно моё решение – в PR/MR ничего не делать и перейти к следующему.
5. Если согласна – исправить и проверить правку линтерами и быстрыми проверками для затронутых файлов, затем сразу подготовить ответ по разделу ответов.

## Ответ и закрытие
Если одна правка закрывает несколько тредов или комментариев, каждому отвечать отдельно. Если исправленных нет, черновики не создавать.

### GitHub
GitHub MCP не умеет добавлять ответ в существующий тред внутри pending-ревью, поэтому ответ публикуется в тред сразу, без pending-ревью:
- Тред – сразу после исправления ответить через `add_reply_to_pull_request_comment`: `commentId` – числовой id первого комментария треда из якоря `#discussion_r…`, не node ID треда, `pullNumber` – номер PR, `body` – `Исправил`. Сразу после ответа закрыть через `pull_request_review_write` с `method: resolve_thread` и `threadId` – node ID треда вида `PRRT_…`.
- Одиночный комментарий или текст ревью – сразу после исправления ответить через `add_issue_comment` с `issue_number` – номером PR. В `body` первая строка – ссылка `html_url` исходного комментария или ревью, вторая – `Исправил`. Без ссылки ответ не связан с комментарием, и при следующем запуске не понять, на что уже есть ответ. Закрыть такой комментарий нельзя.
- Если ответ или закрытие вернули ошибку – перечитать состояние треда и повторять операцию только если ответ не появился или тред остался открытым; иначе считать её выполненной. При повторной ошибке сообщить её мне в отчёте.

### GitLab
- После каждого исправления создать черновик через `create_draft_note` с `in_reply_to_discussion_id` – `id` discussion, `body` – `Исправил` и `resolve_discussion: true`: при публикации ответа тред закроется сам. Это работает и для `individual_note`: ответ превращает его в тред. Запомнить `id` созданного черновика из ответа `create_draft_note`.
- Когда все треды и комментарии обработаны, опубликовать только созданные в этом запуске черновики, каждый через `publish_draft_note` по запомненному `id`, даже если до запуска моих черновиков не было. `bulk_publish_draft_notes` не вызывать: он публикует все мои черновики, включая появившиеся во время запуска вне скилла.
- Если публикация не удалась – сообщить мне ошибку и оставшиеся неопубликованными черновики.

## Итоговая проверка
- Заново получить все треды и комментарии PR/MR со всеми страницами.
- В GitHub каждый исправленный тред должен содержать мой ответ `Исправил` и быть resolved, а на каждый исправленный одиночный комментарий должен быть мой ответ со ссылкой на него. Недостающий ответ дописать, незакрытый тред закрыть повторным `resolve_thread`.
- В GitLab каждый исправленный тред должен содержать мой ответ `Исправил`, а все его заметки с `resolvable: true` – `resolved: true`. Бывшие `individual_note` искать по их `discussion_id`. Незакрытый тред закрыть через `resolve_merge_request_thread` с `discussion_id` и `resolved: true`, а если не помогло – закрыть каждую его заметку через `update_merge_request_discussion_note` с её `note_id` и `resolved: true`.
- После доделок проверить снова. Если после трёх попыток тред всё ещё открыт или ответа нет – перечислить мне его id, ссылку и полученную ошибку.
- Треды и комментарии, по которым исправлений не было, должны остаться без моих новых ответов и без изменения статуса.

## Отчёт в чате
По каждому открытому треду и одиночному комментарию отдельным пунктом списка, без таблиц:
- ссылка на комментарий, автор и `путь:строка`, если замечание касается кода;
- суть замечания одной строкой;
- решение: исправлено, исправлено частично, не согласна, уже было исправлено, нужно моё решение или нужен ответ на вопрос;
- аргументация решения, для исправленных – что и где изменено, для неясных – вопрос ко мне;
- решения агентов – по каждому из двух агентов отдельной строкой:
  - модель, вердикт и суть его аргументации;
  - принят, если вердикт совпал с итоговым решением: `FIX` – исправлено или исправлено частично, `DISAGREE` – не согласна, `ALREADY_FIXED` – уже было исправлено, `NEEDS_DECISION` – нужно моё решение, `UNCLEAR` – нужен ответ на вопрос. Для принятого – почему агент прав и изменил ли он собственное решение;
  - отклонён, если вердикт не совпал с итоговым решением, – почему агент неправ: какой его факт или сценарий не подтвердился проверкой по коду или что он упустил;
  - не ответил – сбой подсессии, пустой ответ или ответ не по формату.
После списка указать результат итоговой проверки, расхождения рабочей копии с PR/MR, если были, и что изменения не закоммичены и не запушены. Последним блоком сообщения – сводка по агентам: по каждой модели и итогом по всем сколько решений принято, из них сколько изменили собственное решение, сколько отклонено и сколько агентов не ответили или упали.
